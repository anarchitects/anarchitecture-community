## Current Verified Requirements

### dbt package installation and subdirectories

dbt itself supports direct Git installation and supports `subdirectory` when the packaged dbt project is nested inside a larger repository. This means the current monorepo layout works for direct `git` plus `subdirectory` consumption through `dbt deps`.

Example from current dbt docs:

```yaml
packages:
  - git: 'https://github.com/dbt-labs/dbt-labs-experimental-features'
    subdirectory: 'materialized-views'
```

Source:

- https://docs.getdbt.com/docs/build/packages

### dbt Hub indexing model

dbt Hub is generated by `dbt-labs/hubcap`, which:

- checks repositories listed in `hub.json`
- opens PRs against `dbt-labs/hub.getdbt.com`
- supports packages hosted on GitHub repositories

Hubcap also documents these relevant constraints:

- the project must be hosted on GitHub
- the project must have a `dbt_project.yml` with a `name:` key
- if the project uses `packages.yml`, that file must live at the root level of the project repository
- only release names using semantic versioning are picked up; `0.1.0` and `v0.1.0` are accepted examples

Sources:

- https://github.com/dbt-labs/hub.getdbt.com
- https://github.com/dbt-labs/hubcap
- https://github.com/dbt-labs/hubcap/blob/main/hub.json

### dbt Hub package review expectations

The current Hubcap best-practices guidance says:

- packages must include a license file detectable by GitHub
- packages should include a README
- packages should document expected warehouse support
- packages requiring a minimum dbt Core version must declare `require-dbt-version` in `dbt_project.yml`
- package git tags must match Hubcap's version parsing expectations and should follow Semantic Versioning

Source:

- https://github.com/dbt-labs/hubcap/blob/main/package-best-practices.md

## What This Means For The Current Monorepo Package

### Supported today

- Direct Git installation from the monorepo is supported by dbt because dbt supports `git` plus `subdirectory`.
- The package has a valid `dbt_project.yml` with `name`, `version`, and `config-version`.
- The package README clearly distinguishes the dbt package from the Python CLI and runtime.
- The repository has an Apache 2.0 license at the repository root.
- The package does not require a warehouse, profiles, or secrets for `validate` and `pack`.

### Risks or gaps for dbt Hub publication

- dbt Hub's current indexing flow is repository-oriented, not subdirectory-oriented.
- Hubcap's public configuration is an org-to-repository mapping in `hub.json`; there is no documented subdirectory field in that index.
- Hubcap expects semver-style release names such as `0.1.0` or `v0.1.0`.
- The current monorepo Git tag convention from [#461](https://github.com/anarchitects/anarchitecture-community/issues/461) is `governance-dbt-package@0.1.0`, which is appropriate for Nx project-scoped Git releases but is not one of the Hubcap-documented accepted release name shapes.
- The package currently lives below the repository root, while Hubcap documents root-level expectations for package repository files.

Bottom line:

- the current monorepo package is ready for direct Git installation
- it is not a clean fit for current dbt Hub indexing as-is

## Publication Options

### Option A — Publish directly from monorepo subdirectory

Assessment:

- Works for direct dbt `git` plus `subdirectory` installation.
- Not cleanly supported by the currently documented dbt Hub ingestion model.

Pros:

- one canonical source repository
- no mirror automation
- no duplicated package repository

Cons:

- no documented dbt Hub support for subdirectory-based package indexing
- Hubcap indexes GitHub repositories, not repository subdirectories
- current monorepo release tags are project-scoped, not plain semver release names
- repository root content would include unrelated workspace assets

Conclusion:

- good for direct Git installs
- not the safest model for dbt Hub publication

### Option B — Split to a dedicated public repository

Example repository names:

- `anarchitects/dbt-anarchitects-governance`
- `anarchitects/anarchitects-governance-dbt`

Pros:

- clean repository root with `dbt_project.yml`, README, and license
- semver tags can be plain `v0.1.0` or `0.1.0`
- simpler fit for Hubcap's repository-based indexing model
- clearer public package landing page

Cons:

- code source moves away from the monorepo
- extra release coordination
- higher risk of drift between monorepo governance work and public dbt package work

Conclusion:

- viable if the team wants the public package repository itself to become the source of truth

### Option C — Mirror the package into a dedicated public repository

Pros:

- monorepo remains the source of truth
- dbt Hub sees a clean, repository-root dbt package
- mirror releases can use plain semver tags compatible with Hubcap
- mirror content can be produced from the existing `pack` artifact

Cons:

- requires mirror automation or disciplined manual mirroring
- introduces one more release surface
- drift is possible if mirror publication fails

Conclusion:

- best fit if the monorepo should remain canonical and dbt Hub compatibility is the goal

## Recommendation

Recommended model:

1. Keep the current monorepo Git tag and GitHub release flow from [#461](https://github.com/anarchitects/anarchitecture-community/issues/461) as the first supported public distribution path.
2. Do not publish the current monorepo subdirectory directly to dbt Hub.
3. Prepare dbt Hub publication through a dedicated public mirror repository whose repository root is the dbt package itself.
4. Use the mirror repository for dbt Hub submission and semver-style release names such as `v0.1.0` or `0.1.0`.

Rationale:

- This preserves the current monorepo source of truth.
- It avoids fighting the current Hubcap repository model.
- It avoids changing the established Nx project-scoped Git tag convention used by the main repository.
- It gives dbt Hub a cleaner package repository with root-level metadata, README, and license.

Fallback:

- If maintaining a mirror repository proves too costly, split the package into a dedicated repository and make that repository the source of truth for public dbt package releases.

## Version Alignment

Version numbers should stay aligned across all publication paths even if the tag format differs.

Recommended alignment:

- `dbt_project.yml` version: `0.1.0`
- monorepo Git tag for direct installs: `governance-dbt-package@0.1.0`
- mirror or dedicated dbt Hub repository tag: `v0.1.0` or `0.1.0`
- dbt Hub package version: `0.1.0`

This is not a separate versioning scheme. It is the same package version represented through two different release mechanisms:

- Nx project-scoped Git tags in the monorepo
- semver-style release names in the dbt Hub-facing repository
